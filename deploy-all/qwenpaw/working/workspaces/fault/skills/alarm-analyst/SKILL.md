# Alarm Analyst

围绕单条活动告警完成根因分析与处置闭环。不是单纯的告警查询技能，也不是只输出诊断结论的模板。

## 加载与最终报告约定

- **查询先直接调用MCP数据工具，不先登录CMDB**：不调用 `cmdb-query__cmdbLogin` 或登录脚本作前置。本技能已加载后不从头重读；参考文档读实际技能目录原文件，空缓存或越界就停止该路径，不再试读或猜路径。
- 分析开始时只读 `references/portal-card-protocol.md` 的1～130行，首屏含合同与完整模板；细则仅按需定位原文件章节，已读则复用。主机CPU/内存/磁盘/进程场景优先定位 `references/rca-iaas.md` 相关章节，协议不当作故障知识。
- **指标最小入参固定为 `mulRes=[{"resId":"<CI_ID>"}]`**，不改成ciId/resCode，不填数字类型ID。定义查询等CMDB真实ci_type/name取得后再发，不用中文别名或cpu猜模型名。实时queryType="0"，历史queryType="1"并带startTime/endTime，二者不可混称。
- **最终正文目标2500～3500字符，上限4500字符（含表格，不是token）**，优先使用协议中的紧凑示例，保留全部固定章节及对象、四类故障摘要、来源、风险和待确认项；合并同类行、重复事实用报告内引用，不逐节重述同一组数值。过程已经展示不等于最终可省略，也不靠删除后半章节凑长度。
- 最终报告保留查询概览及关联分析；跨日接口total只作原查询范围总数，当前页触发值只作离散快照，不能写成单日/三小时总量、全天峰值或健康基线。时间线选关键节点不逐条复制；置信度按协议五项证据评分输出百分比、分项及限制，非统计正确概率，不能声称已实现程序自动评分。
- 用户可见状态用中文：分析证据未覆盖写「部分完成」并说明缺口，关键条件不足写「暂无法继续」；不附英文状态，不改程序内部枚举。根因先分事实与待核验判断；缺本站规则目的/基线时统一写「已确认阈值触发；配置合理性待核验」，全篇不得又断言误报、无即时风险或优先调高阈值。数量/边界不估算，返回超请求范围标限制。
- 完整报告按该协议的固定章节输出；信息缺失、歧义或修正时保留具体待确认项。不要在最后只发总结、通知回执或另一个简版报告。若协议暂不可读，仍保留上述信息，并如实说明限制，不声称格式已经校验。

## 何时使用

- 用户给出了一条具体告警，或上下文中已选中一条活动告警
- 用户希望分析故障根因、影响范围和处置建议
- 用户需要推进闭环：推送分析报告 / 恢复验证 / 清除告警 / 更新状态
- 告警与数据库、MySQL、锁异常、死锁、性能异常、服务异常等主题相关
- 用户描述"某应用新增数据失败""CMDB 插入数据失败"等故障现象

## 何时不使用

- 只看告警列表/数量/分布 → 用 `real-alarm`
- 已有工单上下文继续处置 → 用 `fault-disposal`

## 核心原则

### 执行优先，不要停在"计划调用"

只要当前工作区具备可用工具，就必须先执行真实动作再汇报结果。不需要问"是否继续"，直接做。只有在工具不可用、参数不明确或用户明确要求"先不要执行"时才允许只展示计划。

### MCP 优先
本工作区已启用 `cmdb-query`、`alarm`、`inspection` MCP Server。先直接调用数据工具，不先调用 `cmdb-query__cmdbLogin`、登录脚本、client.login或自建HTTP客户端；已知CI ID直接查详情/关系。仅Driver未加载、工具缺失、连接/传输不可用或协议无法解析时，才回退已有脚本。

1. CMDB 查询 → `cmdb-query__searchCiInstances` / `cmdb-query__getCiInstance` / `cmdb-query__getCiRelations`
2. 活动告警查询 → `alarm__queryHistoricalAlarms`
3. 指标查询 → `inspection__getMetricDefinitions` / `inspection__getMetricData`
4. 只有 MCP 不可用时才回退脚本，只有本地脚本也缺失/不可用时才回退跨智能体（chat_with_agent → query）
5. 回退必须说明真实原因；空结果及可解析的参数、鉴权/权限或业务4xx/5xx错误按Fail Fast处理，不自动转脚本、猜参数重试或换身份。指标定义使用已取得的真实模型名，不先猜cpu或中文别名

### 拓扑驱动分析

不只处理"单个资源告警"，也处理"应用功能失败"：
- 先查应用拓扑，拆出依赖组件链（数据库、中间件、网络、应用、基础资源）
- 再对各组件分层进入故障分析

### 处置总原则：先止血、后修复，按影响范围决策

故障处置遵循「**先恢复业务、再根治根因**」的双轨原则，由**影响范围**决定执行顺序：

- **止血优先（紧急预案）**：故障影响**核心业务 / 大面积用户 / 无冗余可用**时，处置建议列表第一条必须是紧急预案（文本前缀 `🚑 `）——链路或节点切换、流量迁移、主备倒换、熔断降级、限流隔离、配置回滚等，用最快、最稳的动作先把业务恢复到可用，再从容处置根因。
- **直接根治**：**存在有效冗余、影响范围可控，或紧急预案代价高于收益**时，直接给根因处置，不强行加止血步骤。
- **决策要素**：业务等级、受影响用户/业务范围、是否有冗余或备份、恢复时长（RTO）、处置动作的风险与可逆性、是否会引发二次故障。
- **典型示例**：核心链路光模块故障——有备份链路则**先把受影响用户/业务迁移到正常链路恢复访问**，再择机停业务更换光模块；无冗余则边用应急链路承载边最快抢修。

### Fail Fast：接口异常或无数据不做无效重试

任何单个数据源（CMDB、告警上下文、指标查询、跨智能体调用）失败或返回空，都遵循"单次尝试 → 如实记录 → 继续下一步"，不允许为了"凑出结果"而反复重试或换参数试探：

- **单次尝试即可下结论**：接口调用失败（超时、401/403/404/5xx、连接错误）或返回空数据，直接按失败/空处理，不做二次三次重试，不切换参数硬凑
- **指标数为 0 是合法结果**：定义查询成功返回 0 条，仅表示该类型及条件下本次未查到定义，不证明资源没有指标；查询失败也不等于返回 0 条。记录范围与状态后进入下一步
- **降级而不是卡住**：某环节失败不代表整体失败，向用户说明「部分数据已取得」或「该步骤暂无法继续」及具体原因，不原样展示内部英文状态；继续完成其他可执行环节，在总结中说明缺口，不代表故障已修复
- **不要靠切换到其他 skill 来"证明"空结果**：比如指标查询为空，不要绕去 `real-alarm` / 跨智能体反复验证"是不是真的没有"，一次拿到空值即可下结论
- **跨智能体调用同样受此约束**：`chat_with_agent` 超时或无响应，不要重复发起同一请求，按"本地已尽力、协作补充缺失"如实说明

### 故障信息理解（对象识别、现象提取、完整性提示）

在接收告警时整理下面的信息，随后用正常分析链路已取得的数据补充，不为填写摘要增加一轮重复查询。对象、时间锚点和异常现象足够明确时直接执行原流程，不增加人工确认步骤；业务影响或已有处理情况未知，不阻塞正常分析。

**对象识别**

- 从描述中分别识别系统、设备、应用、业务、服务及数据库/中间件实例等主要对象，保留原文称呼，整理为「对象名称、对象类型、对象标识、来源、匹配状态」。名称、类型和标识分别提取；未提供的字段写「未知」，不要为凑齐字段生成标识。
- 标明标识种类（如 CI ID、实例 ID、管理 IP）；区分「输入提及对象」与「查询补充的关联对象」，也区分「用户指定分析对象」与「候选根因对象」。拓扑关联不代表已受影响，更不代表已确认为根因。
- 按语境理解常见缩写和术语，例如数据库语境下 PG 可指 PostgreSQL，但这只能辅助识别类型，不能据此选定某个实例。业务别名优先依据已取得的 CMDB 信息、已配置映射或用户明确说明；模型推断标为「待核验」。
- 无法识别时保留原文并标记「无法识别，待补充」；多个候选列出名称和可用标识供确认，不按类型偏好或列表顺序随意选取。

**现象提取与来源对应**

在当前会话中维护一份故障信息摘要，固定保留「时间、现象、影响、处理情况」四类字段：

| 字段 | 整理规则 |
|---|---|
| 时间 | 分开记录故障开始时间、告警发生时间、请求查询窗口与实际返回的采样起止时间、样本数；未返回的信息写未知。查询窗口不等于实际数据覆盖，告警时间也不等于故障起点。相对时间在日期、时区和上下文明确时转换，并保留原话 |
| 现象 | 分开记录输入描述和查询观测事实，指标附数值、单位、采样时间及已知阈值；「超过告警阈值」不能直接写成「资源耗尽」，候选根因放在根因章节 |
| 影响 | 区分已知影响、潜在影响和待验证项；关联资源清单不是已确认受影响清单，未取得业务验证时不能宣称业务正常或已中断 |
| 处理情况 | 区分故障前已有处理与本次分析动作；每个已知处理动作注明时间、结果和来源，未知部分保留未知。人工反馈、工具执行、仅给建议、通知发送、恢复验证分别说明，通知成功不等于修复完成 |

- 每项信息关联实际可见来源：原始消息/人工补充的可核验短句，或工具名、查询对象、关键返回字段与数据时间；能取得消息 ID、工具调用 ID 时可附上，取不到时不要编造。
- 保留输入原话与整理值的对应关系，不用规范化结果覆盖原始描述。查询补充不冒充原始输入，人工反馈不冒充系统验证，推断明确标为「疑似/待核验」。引用只包含必要片段，隐藏口令、令牌等敏感内容。
- 未提供写「未知（未提供）」；查到空结果写「未查到记录（注明查询范围）」；调用失败写「未取得（注明失败原因）」。未查到或未取得处理记录都不等于「未处理」。
- 告警持续、重复触发或未清除，只说明告警记录状态；没有操作记录或人工反馈时，不能改写为「长期未处理」「未清理」「此前建议未执行」。恢复状态也不能反推某项修复已经执行。
- 趋势与恒定结论仅限实际观测区间，近七日告警不等于七日指标，不能把当前数值套到整段告警时长。样本数须来自返回字段或实际数组统计；可见数据缺末端则写末端未知，统计值注明接口统计，疑似未来时间标异常待核验。缺少现场基线/规则目的时，低CPU占用不证明阈值误配，80%/90%等经验值不是本站标准；不承诺改阈值后告警归零或业务恢复。

**完整性检查与针对性提示**

| 情况 | 提示与执行方式 |
|---|---|
| 信息缺失 | 指出缺少的分析对象、时间范围或异常现象，建议补充能定位目标的名称/标识、发生时间段或具体异常表现，不泛泛要求「补充完整信息」 |
| 表述不清 | 如「昨晚主库有问题」，说明不明确的日期/时段、目标候选或异常表现，提出最少且具体的问题 |
| 内容冲突 | 如设备名与 CI ID 核验不一致、同一事件给出互斥时间，展示冲突值和各自来源，等待确认，不静默择一 |

- 先利用当前消息和已有上下文，不重复询问已经明确的信息。有告警时间时沿用原有查询窗口规则，并说明时间锚点与窗口；完全缺少事件时间时不要把当前时间当作故障时间。确需使用默认近期查询范围时明确标注为查询假设。
- 只有歧义或冲突会改变查询目标/时间范围，或缺少必要参数无法执行时，才暂停依赖它的步骤并请求补充；其余独立且参数明确的查询可继续。没有可靠目标时不执行宽泛的全量查询来猜对象，也不生成已完成 RCA 的结论。
- 完整性提示属于过程回复，不套最终报告 marker。信息足够的常规告警继续原有并行查询、报告和通知流程；不要为未知的影响或处理情况反复追问、重复调用工具。

**人工补充与修正**

- 复用当前对话接收补充，说明「哪个字段：旧值 → 新值，来源为本次人工补充」。保留原始消息和修正依据；明确替换的信息以修正值用于后续分析，仍与其他事实冲突的部分并列保留并请求核验。
- 对象修正后，后续查询切换到新目标；故障时间修正后重新判断查询窗口，保留原告警时间；现象、影响或已有处理变化后，重新检查相关指标选择、根因判断和处置建议。
- 仅在新对象/新窗口等变化使旧数据不再适用时补查必要数据，并标记受影响的旧结论「已被修正/待重评估」。这不是对相同失败请求的重试，不重跑无关步骤。
- 单纯补充或修正信息不自动重新推送通知、创建工单、清除告警或执行处置；若用户另有明确请求，再按原有权限和闭环规则处理。
- 将当前信息和修正说明体现在后续回复/报告中，复用现有会话记录供核验；不要声称已修改原始输入、后台台账字段或实现了跨会话持久化。历史上下文不可见时明确说明并请用户补充必要片段。

### 运维数据查询与整理（数据检索、条件筛选、信息整理）

只使用当前已接入且与故障相关的数据，沿用既有 MCP 优先、并行和 Fail Fast 规则。**本轮不纳入日志，不新增日志查询、日志接入或必填日志行**；不为展示能力额外遍历数据源、扩大窗口或拉取全量历史。

**数据检索与条件留痕**

- 按根资源及已取得的关联资源分别组织查询，记录实际对象名称与 CI ID/实例 ID/IP。按 IP 返回数据时，用可用的资源标识核对归属；同 IP 的主机、数据库和中间件不能混算。无法核验时注明「仅按 IP 匹配，实例归属待确认」。
- 保留实际发送的主要条件：对象、数据类型、时间起止及时区（已知时）、告警状态/等级、指标编码、实时或历史模式、CMDB 查询类型/关系层级，以及已知的分页或返回上限；只使用接口确实支持的参数，不杜撰参数。
- 核对返回记录的对象、时间字段及数据类型是否符合条件；不匹配项不作为目标对象证据，缺少核验字段时保留限制，不能直接当作匹配成功。
- 区分近七日活动告警与近七日全部历史告警、指标定义与指标值、当前指标与历史时序、CMDB 当前配置与历史配置/变更。历史告警不等于历史处理或变更事件；只将已接入且实际查询的数据列为已取得，计划查询不等于已执行。
- 请求范围与实际覆盖分别说明。只取得部分页/对象/时段时，不能宣称全量查询完成；第一页筛选未命中只能写「已返回数据中未匹配到」，不能判定该资源无告警。保留现有分页规则与上限，不为证明空结果追加无界查询或重复失败请求。

**排序、分类与去重**

- 沿用已有排序，在报告中写明字段和方向；查询列表默认可按发生时间倒序，关键事件时间线按正序。首次发生、最近发生与采样时间分别使用，时间未知或无法统一时区的记录单列说明，不编造排序值；先后关系不等于因果。
- 按根资源/关联资源或告警/指标/CMDB/历史事件分类，说明包含、排除对象及状态、级别、指标等实际筛选条件。指标定义的类型筛选不替代指标值的资源匹配。
- 同一来源、同一告警标识的重复返回可去重；没有稳定标识时，仅对能够确认属于同一记录的重复项合并，不按标题或 IP 随意去重。不同对象、不同事件，以及有意义的状态/数值变化保留区分。
- 正文优先展示与故障有关的记录并说明关联理由，不堆全部返回；省略不相关明细不代表它们无异常，不删除原始记录。原始返回数、匹配数、去重数和展示数仅在可核验时列出，无法统计写未知，不把接口全局总数当作目标资源匹配数。
- 人工调整时间、对象或筛选条件时，展示旧条件 → 新条件及影响。仅改变排序/分类时复用已有数据；新范围超出现有覆盖时按请求补查必要部分，未覆盖或受接口限制时明确说明。相关旧结论重评估，不重跑无关步骤、不自动重发通知或执行处置。

**结果状态、时效与来源**

| 实际情况 | 报告表达 |
|---|---|
| 成功且有匹配数据 | 说明匹配对象、范围及已知记录数，展示关键结果 |
| 成功但无匹配数据 | 指定对象、时间和条件下未查到记录；范围不完整时仅说明已返回部分未命中 |
| 结果不完整 | 明确缺失的页、对象、时段或字段及对分析的限制，不冒充完整或空结果 |
| 数据源不可用 | 写「未取得」并注明接口错误、超时等实际原因，不换成「无数据」 |
| 未查询或未接入 | 分别标明，不写成「未发现」或虚构成功记录 |

- 时效问题可与上述状态并存。已知时展示最新采样时间、查询时间及其时差；依据已有采集周期或时效规则判断延迟，不自行设置统一阈值。缺少依据写「时效性待核验」；历史窗口的数据不因早于当前时间就判为延迟，当前 CMDB 数据也不冒充故障时刻快照。
- 关键记录保留可用的资源/告警标识、指标编码、数值、单位和数据时间，注明为何与当前故障有关；同一证据在概览中简述，在现有告警、指标等章节展示明细，不复制全部原始返回。
- 来源指向当前会话真实存在的工具调用记录，可用工具名、查询对象、数据时间及实际可见的消息/调用 ID 定位；仅在真实存在且可访问时提供链接或文件路径。原始结果被截断、不可见或无完整记录时说明限制，不声称已完整留存、永久可查或已导出；引用内容脱敏。

### 异常关联分析（时间关联、对象关联）

复用本轮告警、指标、CMDB及已有人工反馈，形成关键事件时间线与关联证据；不为展示关联而新增日志/APM接入、重复查询或执行处置。关联分析与根因判定分开，场景参考及脚本提示不能代替本次事实。

**时间关联**

- 对主要告警、指标异常、已知变更及人工操作按发生时间正序整理，保留对象、事件内容、时间含义、精度和来源；不改原查询列表的默认排序。首次发生、最近发生、采样及操作时间不混排为同一种时间。
- 同时发生、仅有日期、时间区间重叠或时区/时钟不可比时，说明「先后未能确定」，不补造秒级顺序或传播时差。没有时间的线索单列；早于观测窗口的数据仍注明覆盖限制。
- 说明关联采用的实际时间窗口或可比区间，不自行设定统一“相近”阈值。同属七日查询窗口不等于同时异常，最早告警不自动成为根因，时间先后或两点变化不证明因果。
- 将时间先后与已取得的资源/业务关系、指标或异常记录联合判断；有时间线但缺少关系，或有关系但缺少同步异常时，保留为可能关联或待核验线索。

**对象关联与证据分级**

- 先核对异常记录的对象标识，再使用实际取得的同一对象、承载、依赖、业务归属或共享组件关系。只有通用关联字段时就写「资源关联，方向未知」，不从同IP、名称相似或图中布局推断依赖/部署/传播方向。
- 每条线索说明关联的对象及异常记录、时间联系、关系来源、支持依据和缺口；区分「资源关系已核验」与「异常之间已确认关联」。CMDB关系存在不等于故障已传播，也不等于业务已受影响。

| 关联状态 | 使用条件 |
|---|---|
| 已确认关联 | 明确具体关联命题及其实际证据，或用户明确确认；标明数据核验/人工确认方式。人工确认不冒充独立工具验证，也不自动升级为已确认因果 |
| 可能关联 | 有时间、资源或业务线索，但不足以确认异常联系；写明支持点与其他合理解释 |
| 待核验 | 缺少必要时间、关系或异常记录；给出具体核验方向，不为凑表伪造对象或记录 |
| 本次分析已排除 | 已有证据或人工明确排除的线索；保留原线索、排除来源、原因与适用范围 |

- 多个合理线索并列说明依据和缺口，不强选单一关联。根因百分比用统一证据评分，不按线索/告警数量抬分；缺项计0，不为凑分查询或操作。没有足够线索直接说明缺口，关联表不替代候选根因表。
- 脚本的「同名告警同时出现」「告警增多说明影响扩大」等表述先视为候选提示，回到原始记录核对时间、对象及关系；同名、多告警或数量增加本身不证明传播、复合根因或业务影响扩大，缺少证据时降为待核验。

**人工确认与排除**

- 用户确认、排除或纠正关联时，在当前报告保留「原线索/状态 → 新状态、人工原话、原因、影响到的结论」。原因未说明则写未说明；对象、时间或关系仍有事实冲突时并列提示，不静默覆盖。
- 明确排除的线索不再作为本次根因、影响及建议的支持依据，受影响的旧结论重评估；未被排除的事实保留，排除异常关联不代表删除CMDB关系、原始告警或工具记录。
- 后续分析使用调整后的关联结果，复用现有会话留痕；只确认/排除不自动重查、重发通知、建单、清除告警或执行处置。不声称已改后台字段或跨会话持久化；另有明确查询请求时再按既有规则处理。

### 影响范围与严重程度参考（资源关联、业务关联、严重程度参考）

复用已有CMDB、拓扑、业务映射及人工信息，按报告协议扩充现有 `## 影响范围`；不为填齐维度新增查询、数据源或评分系统。

- 说明关联资源来自CMDB关系、实例内嵌字段还是人工描述；人工关系可作为已有查询的范围依据，但对象标识或关系有歧义时先澄清，不猜实例。只在方向/关系明确时列上游、下游、同层级，否则写通用关联及方向未知。
- 每个可能受影响资源说明关系、来源、影响路径及验证状态；复用第3章证据，不把资源关系直接当作已受影响或故障传播。拓扑返回空不证明无依赖；同机部署不证明应用仅此节点、没有冗余或全部组件受影响。
- 将对象映射到实际取得的系统、服务或业务，以已有的设备/系统/服务/业务/用户一种或多种维度展示影响；缺少映射不按组件名补造业务链，不强查齐全部维度，不推算用户数、损失或失败比例。
- 区分已知影响与潜在风险，每项注明来源和「初步判断/待确认/已验证」；已验证说明验证方式，人工反馈单独标明。无告警不等于业务正常，无业务验证不等于业务中断，用户影响未知不写0。
- 原始告警等级按接口/输入原值保留；另给「故障严重程度参考」，不能直接继承告警等级。只引用实际取得且适用的故障分级规则及命中条件，告警级别映射不冒充故障分级规则。

- 止血/直接根治仍按原有影响范围原则决策，但影响可控、实际受损、有效冗余或无冗余均须有依据；未知时给条件性方案及待核验前提，不虚构备用目标，不把未启用止血解释成影响可控。单纯修正影响/参考等级不自动查询、通知、建单或执行处置。

## 并行执行策略（减少分析耗时）

告警分析涉及多个独立数据源查询，**必须按依赖关系分组并行执行**，不允许无依赖的调用串行排队。

### 并行组划分

**第一波（立即发出，无依赖）**：
- 查智观活动告警上下文（`alarm__queryHistoricalAlarms`，按 ci_id 过滤）
- 查 CMDB 根资源详情（`cmdb-query__getCiInstance`）
- 查 CMDB 拓扑关系（`cmdb-query__getCiRelations`）
- 定位并读取最相关的 rca-*.md 章节（已读则复用；无法匹配/读取须记录原因，不能用报告协议充当故障知识）
- 读取最终报告协议 `references/portal-card-protocol.md`（当前上下文已有则复用）

**第二波（等第一波返回后）**：
- 从拓扑/链路告警提取关联资源 ID → 批量查关联资源告警（可多个 CI ID 并行调用 `alarm__queryHistoricalAlarms`）
- 查指标定义（`inspection__getMetricDefinitions`）+ 指标值（`inspection__getMetricData`）
- 如果本地拓扑为空，才考虑 `chat_with_agent(query)` 补充

**第三波（等第二波返回后）**：
- AI 综合分析 + 推送报告

### 关键约束

- **禁止用 `chat_with_agent` 查询指标数据**：不要通过跨智能体调用 query 智能体来查询指标，直接使用 MCP `inspection__*` Tools。跨智能体调用开销极大（常超时 5-10 分钟），且 MCP 完全能满足需求
- **本地查拓扑优先**：先用 `cmdb-query__getCiRelations` 或链路告警提取对端信息，不要首选 `chat_with_agent(query)` 查拓扑（跨智能体调用可能超时 60s+）
- **跨智能体调用只做补充**：如果本地 CMDB 拓扑为空且链路告警也无法推断对端，才发起 `chat_with_agent`，且用 `submit_to_agent` 后台模式，不阻塞主流程
- **对端设备告警批量查**：多个 CI ID 的告警查询是独立的，必须并行发出

## 完整执行链路（不允许跳步）

```
1. 接收告警 → 提取告警标题、resId/CI ID、告警时间、设备名/IP，整理对象及时间/现象/影响/处理情况并检查完整性（信息足够时直接继续）
2. 查智观活动告警上下文（alarm__queryHistoricalAlarms，活跃状态、近7日历史）
3. CMDB 资源确认（cmdb-query__getCiInstance → cmdb-query__getCiRelations）→ 根资源详情 + ciType + 拓扑关系
4. 变更关联 → 查询故障前24h内相关配置变更/版本升级/割接记录（变更命中=高置信线索）
5. 拓扑关联资源告警查询（硬约束）
6. 指标定义查询（inspection__getMetricDefinitions）→ AI 筛选关键指标 → 查指标值（inspection__getMetricData）
7. AI 综合分析 → 故障类型识别 + 根因判断（六步分析法）
8. 影响范围分析（业务等级/用户范围/冗余备份状态——决定处置建议是否需要把紧急预案条目排最前）
9. 推送分析报告 + 通知推送
10. 恢复验证 → 清除告警 → 更新状态
```

## 关键步骤详解

### 拓扑关联资源告警查询（硬约束）

这是 RCA 完成的**必要条件**，不是可选步骤：

1. 拿到根资源 resId 后，通过 `cmdb-query__getCiRelations` 查询 CMDB 拓扑关系
2. 从拓扑中提取**全部**关联资源 ID（根资源、节点 `_id`、关系边 `src_ci_id/dst_ci_id`）
3. 对这些资源 ID 批量调用 `alarm__queryHistoricalAlarms` 并按 `devId` 本地过滤
4. 如果 CMDB 拓扑为空，可从链路类告警标题中提取对端设备信息作为补充

如果这一步没完成，不能宣称"分析完成"，报告写「分析状态：部分完成」，说明尚未覆盖的关联资源；查询状态直接写具体缺口，置信度如实保留限制。

### 指标分析

优先使用 MCP：

1. 调用 `inspection__getMetricDefinitions(metricType=<模型名>)` 获取指标定义
2. AI 从指标定义中筛选与告警相关的关键指标编码
3. 调用 `inspection__getMetricData(mulRes=[{"resId":"<CI_ID>"}], queryKeys=["<编码列表>"], queryType="0")` 获取指标值
4. AI 结合告警上下文判断哪些指标异常，在 `## 异常指标` 章节中以表格列出

**异常指标识别**：不要列出所有指标，只列出判断为异常的指标，并附带简要异常说明。

### 故障类型识别

拿到拓扑告警 + 指标后，AI 判断故障更像哪一类：
- 基础资源（硬件/虚拟化/容器）
- 网络（时延/丢包/连通性）
- 应用（接口错误/线程阻塞）
- 数据库（锁/死锁/慢SQL/复制延迟）
- 中间件（MQ/Redis/网关）
- 业务逻辑（参数/规则/脏数据）

分析时参考 `references/rca-*.md` 中对应场景的经验知识。

### 推送分析报告

RCA 结论形成后，必须推送分析报告通知（不是可选的）：

```bash
cd skills/alarm-analyst && python scripts/send_analysis_report.py \
  --alarm-id <alarmId> --alarm-title "<标题>" \
  --device-name <设备名> --manage-ip <IP> --level <告警等级> \
  --root-cause "<根因>" \
  --suggestions-json '[{"text":"<紧急预案止血动作>","stage":"emergency"},{"text":"<根因修复动作>","stage":"repair"}]' \
  --abnormal-metrics-json '[{"name":"指标名","code":"metric_code","value":"85.3","unit":"%","reason":"异常说明"}]' \
  --output markdown
```

> **`--level` 必传**：从告警信息中提取等级值（如 `urgent`、`3`、`严重` 等均可），不传则通知中显示为"-"。
> **处置建议一律用 `--suggestions-json`（带 `stage` 字段）**。
> 详见 `references/notification-protocol.md`。推送成功后通知会发送到配置的渠道。
> **审批与风险表达**：报告和通知如实说明建议动作及风险，不隐去危险操作，不改换措辞或调用路径绕过审批。现有脚本参数不变；若调用需要审批或被阻止，按真实状态说明并遵守授权流程。报告生成、通知发送或人工确认均不代表已获修复操作执行授权。

## 输出结构

过程按下列阶段推进；最终回复将已有结果汇总为一份完整报告，不以这些阶段的自由编号标题替换 `portal-card-protocol.md` 的固定章节：

1. 告警接收与解析（对象识别、故障信息摘要、必要的待确认事项；来源和格式见 portal-card-protocol.md）
2. 智观告警上下文确认
3. CMDB / 应用拓扑确认
4. 拓扑关联资源告警查询结果
5. 指标采集与分析
6. 根因判断与影响范围
7. 异常指标（AI 从全部指标中筛选出与告警相关的异常项）
8. 处置建议（`## 处置建议` 单一列表；影响范围大时紧急预案条目排最前、前缀 `🚑 `，见 portal-card-protocol.md）
9. 通知推送结果
10. 恢复验证与状态回写

最终追加 `📊 总结`，第一行给候选根因置信度百分比（统一五项证据支持评分及限制，非统计概率），再列故障性质、根因方向、影响范围、紧急预案实际原因、优先动作、关联资源查询和通知状态。只有已核实影响可控才写无需止血；评分不代替未知项与依据。

如果回复用于 Portal 展示卡片，须遵守 `references/portal-card-protocol.md` 中的 marker 和章节约定。

### 最终回复前自检（只检查已有材料，不增加查询）

1. 在 `## 告警基础信息` 中保留对象识别表、四类故障信息摘要及其来源；信息未知时明确原因，不能只在中间回复出现。
   在 `## 数据查询与整理` 中汇总实际条件、排序筛选规则、返回覆盖、状态及来源；不堆重复明细，不新增查询。
   在 `## 异常关联分析` 中保留时间线、关联依据与状态、必要的人工确认/排除说明；不把资源关系、时间先后或脚本提示直接写成确定因果。
2. 请求窗口和实际采样覆盖分别说明；逐项核对「持续、增长、恒定、已处理/未处理、业务正常/中断」的证据，不足则改为未知或待核验。
3. 输入与接口值不同时说明来源和字段含义，例如原始消息时间与接口首次/最近告警时间，不把不同时间静默合并。
4. 根因、影响、建议与总结保持同一证据口径；通知、修复、恢复验证分别按实际结果填写，未执行不写成功，部分成功不改为全部成功。
   影响路径、验证状态及严重程度参考有依据，原始告警等级不被覆盖；影响或冗余未知时不宣称影响可控、无冗余或业务中断。
   知识来源实际读取、适用性和缺口明确；建议步骤区分生成与执行，高风险动作逐项有前提、风险及人工确认提示。
5. 报告控制在4500字符内并预留后半段，末尾必须到 `## 📊 总结` 的通知状态；超长先压缩重复行，不删依据/待确认/风险，不附全文JSON或无关明细。不加前导语，不为排版重新分析、重发通知或执行操作。

### 处置建议规则（先止血 · 后修复，统一列表，紧急预案置顶+图标）

处置建议的输出模式由 **环境变量 `ALARM_ANALYST_DISPOSAL_DETAIL_MODE`** 控制（在设置页「告警/巡检 → 详细展示模式」开关设置，脚本自动读取）：

值 `false`（默认，**扁平模式**）时，输出 `## 处置建议` 下的单一扁平列表，规则如下。

值 `true`（**详细展示模式**）时，输出三级结构化子节，规则见「详细展示模式（三级结构化）」节。

#### 扁平模式（默认，即当前行为）

处置建议统一输出为 `## 处置建议` 下的一个扁平列表，由第 8 步影响范围分析的结论决定是否需要把紧急预案条目排最前：

**影响范围大（核心业务 / 大面积用户 / 无冗余可用）→ 紧急预案条目排最前，前缀 `🚑 `**：
- 列表第一条（或前几条）为止血/降损动作，文本前缀 `🚑 `：切换到备份链路/节点、把受影响用户/业务迁移到正常路径、主备倒换、熔断降级、限流隔离、回滚引发故障的变更、启用备用电源/制冷等。动作要具体到"切到哪、迁到哪、回滚哪个变更"。
- 紧随其后的是根因处置（修复）动作，不加前缀：更换光模块/板卡、修复线路、扩容、升级版本等，注明可择机安排、避开业务高峰。

**影响范围可控（有有效冗余 / 边缘单点 / 单用户，或紧急预案代价高于收益）→ 只列根因处置动作**，不加 `🚑` 前缀，不强行加止血步骤，避免信息过载。

每个场景的具体止血与修复动作，参考对应 `references/rca-*.md` 中该场景末尾的「⚑ 处置建议」块（含 🚑 紧急预案 / 🔧 根因处置 / 🧭 影响范围决策），仅将其中动作合并为一个列表输出，不再用二级标题分节。

#### 详细展示模式（三级结构化，仅当 `ALARM_ANALYST_DISPOSAL_DETAIL_MODE=true` 时启用）

**先读取环境变量**：在生成报告前检查 `echo $ALARM_ANALYST_DISPOSAL_DETAIL_MODE`，若为 `true` 则按以下规则输出。

`## 处置建议` 下输出三个 `###` 子节（仅此模式允许子节，属受控例外）：

```md
## 处置建议

### 🚨 紧急止血（立即执行）
1. 🚑 将受影响业务流量切换至备用链路 XXX 先行恢复
2. ...

### 🔧 根因修复（计划内操作 / 短期）
1. 更换故障光模块 XXX，建议业务低峰窗口操作
2. ...

### 🛡️ 预防措施（中长期）
1. 建立光模块参数基线定期采集，预测剩余寿命
2. ...
```

- 每级都是编号列表，每个条目必须具体可执行
- 素材来源：`rca-*.md` 各场景「⚑ 处置建议」块中的 🚑 紧急预案 / 🔧 根因处置 / 🛡️ 预防措施
- `--suggestions-json` 中每个条目按所属子节标注 stage：`"emergency"`（紧急止血）/ `"repair"`（根因修复）/ `"prevention"`（预防措施）
- 影响范围可控时：🚨 紧急止血子节可省略，直接从 🔧 根因修复子节开始
- 影响范围可控、且预防措施无需单独成节时：🛡️ 预防措施子节也可省略

**安全边界（必须遵守）**：重启、割接、换件、配置下发、删除、主从切换等高风险动作只输出建议，并注明"需人工确认审批后执行"；数字员工不直接执行，结论附证据链。

**禁止事项**：
- **禁止未经用户确认自动创建工单**：不要在分析流程中直接调用工单 API 自动建单；仅允许 Portal 在分析完成后弹出确认框，且只有用户明确确认后，才可由 Portal 后端受控调用工单创建能力
- **报告正文禁止使用 `---` 分隔线**：`---` 仅用于 `PORTAL ALARM ANALYST CARD MODE` 标志行与正文之间的唯一分隔，正文内出现 `---` 会导致卡片解析截断
- **扁平模式下，处置建议不要再用 `### 🚑 紧急预案` / `### 🔧 根因处置` 二级标题分节**：统一放在同一个列表里，靠 `🚑 ` 前缀和排序区分
- 每条建议必须是具体可执行的动作，不要给出笼统的方向性描述

## 拓扑可视化

当 CMDB 或 query 返回拓扑关系时，**必须**在报告正文中输出一个 ` ```echarts ` 代码块：

- **优先使用 `series.type='tree'`**（`orient='LR'`，从左到右分层），根节点用实际应用名或核心资源名
- 仅当拓扑呈现多对多网状依赖时，才退化使用 `series.type='graph'`
- 禁止只用 markdown 表格或文字描述拓扑而不给 echarts 代码块
- 保留 query 返回的 echarts 代码块，不要改写成纯文字
